# Stable prompt prefix for caching

Providers with prefix caching (vLLM's automatic prefix caching, LiteLLM in front of it, OpenAI, Anthropic) reuse the work for the longest leading part of a request that matches an earlier one, and recompute everything from the first differing token on. Images count as tokens in that prefix, and reference photos are by far the largest part of an identification request. So the attachments are each Person's reference images first, in the configured order, and the camera snapshot last; the prompt points at the snapshot as "the last attached image". The generate_data text starts with the fixed response instructions, then the household list and reference mapping (the same for every detection run), and ends with the re-check, move check or handoff framing, the only part that changes between kinds of run. The evaluate state names the snapshot's image number, which is the same for a given set of Persons. A detection run then sends the same prefix every time, up to the new snapshot. Rationale: the snapshot is the one thing guaranteed to differ, so anything after it can never be reused; with it first, every reference image was encoded again on every run. Trade-off: the order is a contract the code and the prompts must keep together, and a model may weigh the last image differently from the first; the text names the snapshot explicitly to offset that. Limits outside this integration: HA's AI Task system prompt for generate_data includes the current time to the second, so the prefix breaks there before our text unless a proxy normalizes that line; core's OpenAI evaluate entity sends no system prompt, other evaluate entities may differ. Re-checks, move and handoff checks list only some Persons, so they share less with a detection run.
